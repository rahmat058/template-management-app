# Taste

- Prefers UI elements to use their conventional, native-looking visual pattern rather than custom button/pill styling — e.g. tab strips should read as real tabs (full-height, clear bottom indicator, active-tab background) instead of chips that look like buttons. Confidence: 0.6
- Expects detail-level layout/ordering of controls inside a component to be intentional and tidy (icon placement, ordering of name/status/close affordances). Confidence: 0.5
- Wants hover/active feedback on interactive controls to use a consistent primary-color tint at reduced opacity (e.g. `bg-primary/10` + primary text) rather than neutral gray/surface tints, applied uniformly to all sibling controls in a component. Confidence: 0.5
- In a selected/active state, text and icons should render in the primary color (`text-primary`) rather than the default foreground color, so the whole active element reads as one primary-colored unit. Confidence: 0.55
- Prefers interactive elements to size themselves from their parent layout (e.g. inherit full row height via `items-stretch`/`h-full`) instead of hard-coded fixed dimensions, keeping adjacent controls the same shape. Confidence: 0.45
- Prefers branding to use real image assets from `public/images/` with descriptive kebab-case names (e.g. `company-logo.png`, `footer-logo.png`) instead of generic icons or CSS shape stand-ins (e.g. a colored pill rectangle as a footer logo). Confidence: 0.5
- Prefers horizontal separators rendered as a thin (1px) `line` shape in an existing palette color, rather than relying on heavier borders; the rule should sit close to the content it groups (tight gap) so the band reads as one block, not float with a large void beneath it. Confidence: 0.5
- Expects elements to align to the same shared page/content margins so their left/right edges line up with neighboring content (e.g. footer row spanning the same edges as the table, footer note starting on the left margin with the logo flush right). Confidence: 0.45
- Prefers logo/brand images to fill their box edge-to-edge, accepting slight cropping of surrounding whitespace, rather than letterboxing with empty bands — i.e. default image elements to `objectFit: 'cover'` instead of `'contain'`. Confidence: 0.45
- Prefers "template" terminology over "project" throughout the product — UI labels, `aria-label`s, and docs should say "Template name" rather than "Project Name", since the edited entity is a template not a project. Confidence: 0.5
- Groups controls with the element they operate on (e.g. undo/redo icons placed immediately beside the name input they act on) rather than bundling them into a separate generic action group. Confidence: 0.45
- Prefers secondary/utility panels (e.g. the saved-templates library) to span the full width of the canvas and be docked flush to its bottom edge as part of the layout, rather than floating as a narrow overlay card or a narrower page-width centered bar. Confidence: 0.55
- Prefers bottom utility bars to be a full-width band docked into the canvas as a layout/flex child (shrinking the scroll area) rather than an absolutely-positioned overlay that permanently covers the bottom of the document; content should stay scrollable/reachable. Confidence: 0.45
- Iterates on UI layout through successive refactor requests and is comfortable reversing an earlier positional decision (e.g. page-width centered dock → full-width bottom bar) — treat the latest layout directive as authoritative. Confidence: 0.45
- Communicates design intent primarily via reference screenshots and expects the UI to be matched closely to the pictured layout (e.g. "make it like this screenshot"), including control placement such as putting a save action inline in a panel header. Confidence: 0.5
- Favors a compact/dense UI: panels and bars should hug their content rather than pad themselves out (avoid generous `min-h` values), use tight padding, and collapse stacked rows into single-row layouts. Confidence: 0.55
- Wants an item's action controls (e.g. Open button, ••• menu) placed inline on the same row as the item name, right-aligned and aligned with the name line, instead of on a separate row beneath the content block — and expects those inline actions to be vertically aligned consistently with the name. Confidence: 0.5
- Explicitly asks for a "beautiful/compact UX" — expects aesthetic polish and density to be treated as first-class requirements alongside functional correctness when asked to adjust layout. Confidence: 0.45
- Expects preview/thumbnail views (e.g. the sidebar page previews) to be faithful WYSIWYG mini-renders of the real content — reusing the actual element components in a non-interactive mode, at true page proportions with real text/colors/z-order — rather than approximate placeholder blocks, and to reflect content edits immediately. Confidence: 0.5
- Wants non-editable/blocked controls (e.g. `readOnly` inputs) to advertise their state both on hover (`cursor-not-allowed`) and visually (muted/disabled surface + dimmed text), not just look inert — the field should _feel_ disabled, not merely refuse input; favor the conventional `disabled:`/`not-allowed` affordance already used elsewhere in the design system. Confidence: 0.55
- Prefers control-state styling to live centrally in the shared design-system component (e.g. `read-only:`/`disabled:` variants in `Input`'s base classes) so every consumer inherits it, rather than repeating ad-hoc per-instance classes; when asked to "create" a state style, expects it added to the reusable component, not sprinkled at call sites. Confidence: 0.5
- Wants the entire interactive field row to behave as one control — `cursor-pointer` on the whole row (not just the small widget inside it, e.g. the color swatch) plus a row-level hover/focus-within border change, so clicking anywhere in the row triggers the action. Confidence: 0.5
- Explicitly asks for "better micro interaction" — expects interactive controls to carry polished micro-interactions such as hover/focus transitions, subtle scale-ups on the inner widget, and animated affordances, treated as a first-class part of the request rather than optional polish. Confidence: 0.5
- Prefers native form controls restyled to match the design system instead of keeping default browser/OS chrome (e.g. a `<select>` restyled with `appearance-none` + a custom chevron icon, pointer cursor, and hover/disabled states). Confidence: 0.5
- When native chrome can't be styled (e.g. the OS-rendered `<select>` popup with its blue highlight), prefers replacing the control entirely with a fully custom-styled overlay/listbox rather than accepting the default look — willing to accept the extra cost of reimplementing keyboard/ARIA behaviour to get a consistent app-matched appearance. Confidence: 0.5
- Expects custom-styled overlays/popups to carry the same design-system polish as the rest of the UI (surface card with border + shadow, rounded corners, consistent padding/gap, primary-tinted active row, subtle enter animation that respects `prefers-reduced-motion`, viewport-aware flipping/clamping so they're never clipped or off-screen). Confidence: 0.45
- Expects a repeated control's styling/behaviour fix to be applied consistently everywhere that control appears, favoring one shared reusable component (e.g. a `ColorInput` used by Text Color, Page Background, Shape Fill/Border, Table Border) over per-instance tweaks to only one instance. Confidence: 0.45
- Prefers seeding to reset to a known clean state — clear/wipe the collection first, then insert the default data set — rather than idempotent upserts or additive seeding that tolerates pre-existing rows. Confidence: 0.45
- Wants console/terminal log lines prefixed with a relevant emoji icon per step, including a themed emoji on the completion message (e.g. 🌱 "Seeding complete"). Confidence: 0.55
- Expects the emoji-iconed log style to be applied consistently across all of an app's console output — server/startup logs (`🔌 Connected to MongoDB`, `🚀 API listening on…`), shutdown/failure/retry lines, and the seed runner — rather than only in the one file just touched. Confidence: 0.5
- Prefers all test files collected in a single root `test/` directory that mirrors the `src/` layout in subfolders (`test/lib`, `test/middleware`, `test/modules`, `test/seed`, `test/validators`), rather than tests colocated next to the code they cover. Confidence: 0.8
- Wants the test command to run test suites one by one (sequentially, e.g. Jest `--runInBand`) instead of in parallel workers. Confidence: 0.75
- Expects the rationale behind non-obvious technical choices to be explained — asks "why did you add this / what's the purpose" for flags and config it didn't request, so changes should come with their purpose, tradeoffs, and how to revert. Confidence: 0.5
- Wants all backend API responses to go through a single shared envelope helper from `backend/src/lib/http.ts`: success is `{ success: true, data }` via `sendSuccess`, failure is `{ success: false, error: { message, code, details? } }` via `sendError`, and `sendNoContent` for 204 — rather than ad-hoc per-route response shapes. Confidence: 0.75
- Does not want the HTTP status code duplicated inside the JSON response body — the envelope carries only `success`/`data`/`error`, and the status is expressed solely in the HTTP response status. Confidence: 0.7
- Treats the API response envelope as a cross-cutting contract: when it changes, the frontend transport (`frontend/src/lib/api.ts`) and the backend tests must be updated together in the same change, since tests assert the exact shape. Confidence: 0.65
- Wants reusable helper/generic functions extracted out of entry-point or orchestration files (e.g. `connectWithRetry`, `wait` living in `server.ts`) into a shared common utility folder (`src/lib/`) and imported back, leaving the entry file as pure bootstrap — favors many small single-concern utility modules over inline local definitions. Confidence: 0.55
- Wants routes and their handlers documented in code: every route definition (and the controller handler behind it) should carry its own explanatory comment placed directly above it, with the wording kept consistent across the route and controller so the two read as a matched pair. Confidence: 0.6
- Prefers deprecated API usage flagged by the IDE/LSP (e.g. Zod v4's no-op `.finite()`) to be cleaned up and removed rather than left in place, and expects the editor diagnostic to actually clear afterwards. Confidence: 0.45
- Keeps comments strictly to a single line each — when a comment spills onto a second line it should be condensed back into one line (e.g. folding a route's ordering caveat into the same sentence) rather than left as a multi-line block. Confidence: 0.5
